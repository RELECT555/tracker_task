## 0. Зачем

Колокольчик говорит, что что-то сломалось, но этого мало:
- нельзя увидеть все текущие проблемы разом;
- нельзя понять, повторяется ли проблема;
- нельзя посмотреть, что было вчера или на прошлой неделе.

Сам поповер выглядит невнятно. Прочитанное уведомление показано серым текстом, статуса нет, «сейчас: 1» дублирует заголовок.

Цель — **дежурная панель синхронизации**. Это общая для всех картина: что сломано сейчас, что было, как часто повторялось и что с этим делать. Плюс понятный поповер со ссылкой на панель.

### Цели
1. Страница `/roadmap/sync` («Синхронизация») со списком эпизодов проблем, фильтрами, историей и подсказкой «что сделать».
2. Журнал эпизодов: каждое открытие и закрытие проблемы сохраняется отдельной записью.
3. Переделанный поповер: иконка вида, цвет статуса, понятная вторая строка, ссылка «Все уведомления →».

### Не цели
- Личные «прочитано» на странице. Страница показывает состояние, а прочитанность остаётся только в колокольчике.
- Ручное закрытие, «взять в работу», назначение ответственного, комментарии.
- Графики и аналитика по проблемам.
- Новые виды проблем или изменение правил сторожа: пороги и подавление остаются как в v1.

### Анти-цели
- Планировщик видит проблемы чужих проектов или глобальные проблемы PAT и webhook.
- Страница выдаёт текст, которого нет в уведомлении. Например, сырой текст ошибки без очистки секретов.
- Журнал без ограничения размера.

## 3. Данные

### 3.1. `RoadmapAlertEpisode` (`roadmap_alert_episodes`)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | |
| `alertId` | uuid FK → `RoadmapAlert` (cascade) | |
| `generation` | int | номер эпизода, равен `alert.generation` при открытии |
| `kind` | varchar(50) | копия из проблемы |
| `projectId` | uuid? FK → `RoadmapProject` (cascade) | null для глобальных |
| `openedAt` | timestamptz | |
| `resolvedAt` | timestamptz? | |
| `resolution` | varchar(20)? | `fixed` \| `obsolete` |
| `details` | Json | последние известные данные (счётчик, HTTP-статус, очищенный текст ошибки) |
| `peakCount` | int? | максимальный `details.count` за эпизод |

- Уникальность `(alertId, generation)`.
- Индексы: `(projectId, openedAt desc)` и `(resolvedAt)`.
- Миграция одна, аддитивная.

### 3.2. Запись сторожем
- **open.** В той же транзакции, где открывается эпизод проблемы, создать запись эпизода через `createMany({ skipDuplicates: true })`. Если в транзакции что-то упало, откатываются и проблема, и эпизод, как уже сделано для уведомлений.
- **refresh.** Обновить `details`. `peakCount` поднять, если текущий `count` больше.
- **resolve.** Тем же условным переходом, что закрывает проблему, проставить эпизоду текущего поколения `resolvedAt` и `resolution`. Писать только если переход выиграл.
  - Для `fixed` в `resolvedAt` пишется `clearSince` проблемы, то есть момент, когда условие действительно ушло, а не момент закрытия сторожем (он на 10 минут позже).
  - Для `obsolete` пишется `now`.
  - Так длительность на странице честная, и короткие сбои не выглядят десятиминутными.
- **Существующие открытые проблемы** (открылись до миграции) не имеют записи эпизода. При первом refresh или resolve её нужно создать (upsert по `(alertId, generation)`) с `openedAt = alert.openedAt`.
- **Очистка** в ежедневном шаге сторожа: удалить закрытые эпизоды, у которых `resolvedAt` старше 90 дней.
  - Существующее правило «удалить закрытые проблемы без уведомлений» дополнить: удалять проблему, только если у неё нет ни уведомлений, ни эпизодов. Иначе каскад сотрёт историю проблем, у которых не было получателей.
- **Секреты.** `details.error` уже очищен (`redactSecrets`) при записи здоровья импорта. Писать его в эпизод только в таком виде.

## 4. Доступ

| Кто | Видит |
|---|---|
| Администратор | все эпизоды, включая `azure_auth` и `webhook_silent` |
| Планировщик проекта (`RoadmapProjectAccess.role = planner`) | только эпизоды с `projectId` своих проектов, без глобальных и без `webhook_silent` (как в правилах получателей v1) |
| Остальные (наблюдатели, без доступа) | ничего: API отвечает 403, пункт меню скрыт |

- Фильтр по доступу применяется в запросе к базе, а не в UI.
- Фильтр `projectId` в запросе можно задать только для проекта, к которому у пользователя есть доступ. Иначе ответ 403.
- В ответ `GET /roadmap/notifications/summary` добавить поле `canViewSyncProblems: boolean`: `true` для администраторов и для тех, у кого есть хотя бы один доступ `planner`. По нему веб показывает пункт меню и ссылку в поповере.

## 5. API

`GET /roadmap/sync-problems?status=active|resolved|all&projectId=&cursor=&limit=30`

**Строка списка — это проблема (ключ «вид + проект»), а не отдельный эпизод.** В строке показан её последний эпизод, прошлые эпизоды открываются через «История».
- Это `roadmap_alerts` с последним эпизодом. Проблема, сломавшаяся трижды, занимает одну строку с «3-й раз за 7 дней» и историей из двух прошлых эпизодов.
- В список попадают только проблемы, у которых есть хотя бы один эпизод в журнале.

Параметры:
- `status` по умолчанию `active`:
  - `active` — проблемы со `state = open`;
  - `resolved` — со `state = resolved`;
  - `all` — все.
- Сортировка:
  - `active` — по `openedAt desc`;
  - `resolved` — по `resolvedAt` последнего эпизода desc;
  - `all` — сначала активные, затем закрытые по `resolvedAt desc`.
- Курсорная пагинация, как у уведомлений. Лимит от 1 до 50, по умолчанию 30.

Ответ: `{ items: SyncProblemDto[], nextCursor, counts: { active: number }, projects: { id, name }[] }`.
- `counts.active` считается с учётом доступа и фильтра проекта.
- `projects` — проекты, по которым пользователь может фильтровать. Для админа это все проекты с `syncedAt`, для планировщика — только те, где он `planner`. Из этого списка строится выбор проекта; отдельный эндпоинт не нужен.

`SyncProblemDto`:
```
{
  alertId,               // ключ строки и параметр для /history
  episodeId,             // последний эпизод
  kind, projectId, projectName,
  title,                 // formatAlert по актуальным details
  body,                  // очищенный текст ошибки или null
  status: 'active' | 'fixed' | 'obsolete',
  openedAt, resolvedAt,  // ISO
  peakCount,             // для sync_errors / sync_conflicts
  recurrence7d,          // эпизоды этого ключа, открытые за 7 дней, заканчивающихся openedAt последнего эпизода (включая его)
  historyCount,          // сколько прошлых эпизодов (все, кроме последнего) лежит в журнале
  hint,                  // «что сделать», текст из §6
  action: { label, link } // кнопка перехода; ссылка с учётом роли (как в v1: не-админам — план)
}
```

`GET /roadmap/sync-problems/:alertId/history?limit=20` возвращает все эпизоды этого ключа, кроме последнего, новые сверху.
- Формат: `{ episodeId, openedAt, resolvedAt, resolution, peakCount, details }`.
- Правила доступа те же. Чужой или невидимый ключ — 404.

`recurrence7d` и `historyCount` для страницы считаются одним агрегатом по `alertId` страницы, без запроса на строку.

DTO и zod-схему запроса положить в `packages/shared` рядом с `roadmap-notifications.ts`.

## 7. Веб

### 7.1. Страница `/roadmap/sync`
- **Маршрут и меню.**
  - `routes.roadmapSync = '/roadmap/sync'`.
  - В меню пункт «Синхронизация» после «Аналитика». Иконка `Activity` из `lucide-react`.
  - Показывается, только если `canViewSyncProblems`.
  - Хлебные крошки: «Главная / Синхронизация».
- **Шапка.**
  - Заголовок «Проблемы синхронизации».
  - Под ним счётчик активных: «Активных: N» или «Активных проблем нет».
  - Фильтр статуса: сегменты «Активные / Исправленные / Все», по умолчанию «Активные».
  - Выбор проекта: «Все проекты» + проекты, доступные пользователю.
  - Фильтры хранятся в query-параметрах (`?status=&project=`), чтобы ссылкой можно было поделиться.
- **Строка эпизода.**
```
[иконка вида]  Ошибки отправки в Azure: 5 назначений          ● Активна
               OKR · открыта 12 мин назад · 3-й раз за 7 дней
               Откройте назначения с ошибкой, проверьте…      [Открыть план →]
               ▸ История (2)
```
  - **Иконка и цвет.** Иконка зависит от вида. Цвет показывает статус: активна — красный (destructive), исправлена — зелёный (success), больше не актуальна — серый (muted). Используются существующие токены темы, без новых цветов.
  - **Время.** Для активных — «открыта … назад». Для закрытых — «длилась 25 мин · исправлено вчера в 14:05». Полное время показывается в `title`.
  - **«N-й раз за 7 дней»** показывается, только если `recurrence7d ≥ 2`.
  - **Пик.** Если `peakCount` больше текущего числа, рядом приписка «макс. N».
  - **Тело.** Если `body` есть (текст ошибки импорта), он показывается моноширинным шрифтом, свёрнут до двух строк и раскрывается по клику.
  - **«История (N)»** раскрывает прошлые эпизоды того же ключа: запрос к `/history`, компактный список «открыта · длилась · чем закрылась».
- **Обновление.** Опрос раз в 60 секунд и при фокусе окна.
- **Состояния.**
  - Загрузка — скелетон.
  - Пусто для «Активных»: «Всё работает — активных проблем синхронизации нет».
  - Пусто для остальных фильтров: «За последние 90 дней проблем не было».
  - Ошибка — `ErrorNotice`.
  - 403 — «Нет доступа к проблемам синхронизации».
- **Ширина 375 px.** Строка перестраивается в колонку, кнопка во всю ширину, без горизонтальной прокрутки.
- **Демо-режим.** Пустой список, `counts.active = 0`, `canViewSyncProblems = true` для админа.

### 7.2. Поповер колокольчика (переделка)
```
┌ Уведомления ───────────────────── Прочитать все ┐
│ [⚠] Ошибки отправки в Azure: 1 назначение   ●   │  ← жирный, пока не прочитано
│     OKR · 3 мин назад · Активна                 │  ← статус цветом
│ [🔑] Azure DevOps отклоняет PAT (HTTP 401)       │
│     вчера · ✓ Исправлено                        │
├─────────────────────────────────────────────────┤
│                         Все уведомления →        │  ← если canViewSyncProblems
└─────────────────────────────────────────────────┘
```
- Слева иконка вида, та же, что на странице, в круглой подложке цвета статуса.
- Заголовок жирный и основного цвета, пока уведомление не прочитано. Прочитанное — обычный вес, тоже основной цвет, а не серый. Вторичный цвет только у второй строки.
- Вторая строка: «проект · когда · статус». Статус: «Активна» (красный), «Исправлено» (зелёный), «Больше не актуально» (серый).
- «сейчас: N» показывается, только если актуальное число отличается от числа в заголовке: «сейчас: 3».
- Строки разделены тонкой линией, у строки есть фон при наведении и фокусе.
- Внизу ссылка «Все уведомления →» ведёт на `/roadmap/sync`. Если прав на страницу нет, ссылки нет.
- Общие пиктограммы и цвета статуса вынести в одно место (`notification-view.ts` или соседний файл), чтобы страница и поповер не расходились.

## 8. Тесты
1. **Сторож.**
   - Открытие создаёт эпизод.
   - refresh обновляет `details` и поднимает `peakCount`, но не опускает его.
   - Закрытие проставляет `resolvedAt` и `resolution` только при выигранном переходе.
   - Два параллельных `evaluate()` создают один эпизод.
   - Открытая до миграции проблема получает эпизод при первом refresh.
   - Очистка удаляет закрытые эпизоды старше 90 дней.
2. **API: доступ.**
   - Админ видит всё.
   - Планировщик видит только свои проекты и не видит `azure_auth` и `webhook_silent`.
   - Наблюдатель получает 403.
   - Фильтр по чужому проекту — 403.
   - `/history` чужого ключа — 403 или 404.
3. **API: данные.**
   - Сортировка и курсор для каждого `status`.
   - `recurrence7d` считает эпизоды того же ключа за 7 дней.
   - `counts.active` учитывает доступ.
   - `canViewSyncProblems` в summary.
   - Ссылки в `action` зависят от роли.
4. **Веб** (`node --test`): статус в метку и цвет, правило показа «сейчас: N», «N-й раз за 7 дней», форматирование длительности.
5. **Браузер.**
   - Страница под админом и под планировщиком.
   - Фильтры и ссылка через query.
   - Раскрытие истории.
   - Поповер в светлой и тёмной теме.
   - 375 px.

## 10. Решения, принятые без заказчика
1. **Маршрут.** `/roadmap/sync`, пункт меню «Синхронизация», а не раздел админки: планировщикам админка закрыта.
2. **Видимость.** Планировщики видят только свои проекты, без PAT и webhook. Наблюдатели не видят страницу.
3. **Срок хранения журнала** — 90 дней, как у уведомлений.
4. **Нет личных «прочитано» и ручного закрытия:** страница только показывает состояние.
5. **Повтор** считается за 7 дней, заканчивающихся открытием последнего эпизода. Так «3-й раз за 7 дней» не пропадает у давно закрытых проблем.
6. **Строка списка — проблема, а не эпизод.** Повторы видны счётчиком и историей, а не дублями строк.
7. **Длительность** считается до момента, когда условие ушло (`clearSince`), а не до закрытия сторожем.
8. **Список проектов для фильтра** приходит в ответе страницы и содержит только проекты, по которым пользователь может фильтровать.
9. **Очистка проблем** не удаляет проблему, пока у неё есть эпизоды в журнале.
