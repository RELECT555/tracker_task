# ТЗ: Уведомления о здоровье синхронизации (v1)

Дата: 2026-11-16. Статус: реализовано.

Перед началом прочитай `docs/13-roadmap.md` (раздел про двустороннюю синхронизацию) и файлы из §1.

## 0. Зачем

Сбои синхронизации с Azure DevOps сейчас никто не замечает. Статусы `error`/`conflict` видны только в строке плана и на вкладке «Интеграции → Проекты». Отказ PAT и падение импорта по cron вообще пишутся только в лог (`roadmap.service.ts:271`). Администратор узнаёт о проблеме случайно, часто — когда план и Azure уже разошлись.

Цель v1 — **чтобы ответственный человек узнал о проблеме синхронизации в течение нескольких минут, один раз, и получил ссылку туда, где её чинить.**

### Цели
1. Колокольчик в шапке Roadmap со счётчиком и списком уведомлений.
2. Уведомления о пяти видах проблем (§4), адресованные администраторам и планировщикам проекта.
3. Одно уведомление на один эпизод проблемы, «исправлено» — когда она ушла.

### Не цели (v1)
- Почта, Telegram, push в браузер. Слой каналов можно добавить позже поверх той же модели.
- Личные настройки подписок («что мне присылать»).
- Websocket/SSE — используем опрос, как везде в приложении.
- Уведомления по каждому назначению отдельно.
- Уведомления исполнителям о назначенных часах (Azure сам уведомляет исполнителя задачи при записи).
- Перегрузка людей, выдача доступа и прочие «действия людей» — кандидаты на v2 (точечные события, §11).

### Анти-цели (провал, даже если «работает»)
- Лавина: больше одного уведомления на эпизод проблемы у одного человека (например, по уведомлению на каждый 5-минутный цикл импорта).
- Дубли из-за нескольких инстансов API.
- Мигание «проблема / исправлено» при повторной отправке назначения (`error → pending → sending → error`).
- PAT, секрет webhook или заголовки авторизации в тексте уведомления.
- Уведомления о штатных состояниях (`skipped`, `pending`, `sending`).

## 2. Выбранный подход: «сторож состояния»

Рассмотрены три варианта:

| Вариант | Суть | Почему выбран / нет |
|---|---|---|
| **А. Сторож состояния** ✅ | Раз в минуту одна задача считает агрегаты «здоровья» и открывает/закрывает **проблему** по ключу `вид + проект`. Уведомления создаются только на переходе «нет проблемы → есть проблема». | Одно место в коде, не трогаем 15 мест записи статусов; дедупликация и защита от лавины — по построению; безопасно на нескольких инстансах. Цена — задержка до ~1 мин и агрегированный текст («5 назначений с ошибкой»). |
| Б. События в коде | `notify()` в каждом месте смены статуса. | ~15 точек, новую легко забыть; всё равно нужен антиспам; сбои cron/PAT без сохранённого состояния не поймать. |
| В. Гибрид | А + точечные события для редких действий людей. | Не нужен в v1; это путь развития (§11). |

Выбран **А** (решение заказчика).

## 3. Модель

Две сущности: **проблема** (одна на ключ, живёт долго, открывается и закрывается) и **уведомление** (копия проблемы для конкретного человека, снимок на момент открытия).

### 3.1. `RoadmapAlert` — проблема

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | |
| `key` | varchar(150), **unique** | `${kind}:${projectId}` или `${kind}:global` |
| `kind` | varchar(50) | вид из §4 |
| `projectId` | uuid? FK → `RoadmapProject` (cascade) | null для глобальных |
| `state` | varchar(20) | `open` \| `resolved` |
| `generation` | int, default 0 | номер эпизода; +1 при каждом открытии |
| `openedAt`, `resolvedAt` | timestamptz? | |
| `resolution` | varchar(20)? | при закрытии: `fixed` (условие ушло само) \| `obsolete` (проблема потеряла смысл: проект удалён или выведен из записи в Azure, интеграция отключена) |
| `clearSince` | timestamptz? | с какого момента условие ложно (для задержки закрытия, §5.3) |
| `details` | Json | данные для текста: счётчики, HTTP-статус, обрезанный текст последней ошибки |
| `updatedAt` | timestamptz | |

### 3.2. `RoadmapNotification` — уведомление пользователя

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | |
| `userId` | uuid FK → `User` (cascade) | |
| `alertId` | uuid FK → `RoadmapAlert` (cascade) | |
| `generation` | int | эпизод проблемы |
| `kind`, `projectId` | копия из проблемы | для фильтров и ссылки без join |
| `title` | varchar(200) | готовый текст на русском |
| `body` | varchar(1000)? | |
| `readAt` | timestamptz? | |
| `createdAt` | timestamptz | |

- Уникальность `(alertId, generation, userId)` — защита от дублей между инстансами.
- Индекс `(userId, readAt, createdAt desc)`.
- «Исправлено» — это не отдельная запись: состояние берётся из проблемы. Если `alert.generation == notification.generation` и `alert.state == 'open'`, проблема актуальна. Иначе она исправлена или сменилась новым эпизодом.

**Таблицы новые** (`roadmap_alerts`, `roadmap_notifications`). Старая `notifications` остаётся как есть, `@@ignore`.

### 3.3. Сохранение «здоровья», которого сейчас нет

Добавить в `RoadmapAzureProjectState`:

| Поле | Когда пишется |
|---|---|
| `importFailingSince` timestamptz? | Время первой неудачи в текущей серии. Ставится при неудачном импорте, если пусто. Сбрасывается в null при успешном импорте |
| `lastImportError` varchar(500)? | Текст ошибки при неудаче. Без секретов, обрезан |
| `lastImportFailedAt`, `lastImportOkAt` | timestamptz? |
| `lastImportChangedAt` timestamptz? | Время, когда импорт **по опросу** (cron или ручной «Обновить проект из Azure») нашёл хотя бы один изменённый work item. Импорт по webhook это поле не трогает |

Порог задан **временем, а не числом попыток**. Cron работает на каждом инстансе, ручной импорт и webhook тоже дают попытки, поэтому число неудач зависит от числа инстансов.

**Где писать.** Запись успеха и неудачи вынести в одну функцию `recordImportOutcome(projectId, outcome)`. Её вызывают **все** пути импорта:
- `runProjectImport` в `roadmap.service.ts` (cron и ручной);
- `flushWebhookImports` (`roadmap-azure-sync.service.ts:2144`), где импорт сейчас идёт напрямую через `importer.importWorkItems` и только пишет лог;
- прочие прямые вызовы `importer.importWorkItems` (`roadmap-azure-sync.service.ts:1180, 2005`).

Очереди импорта перестраивать не нужно, меняется только запись результата.

Глобальное состояние доступа к Azure хранится в `system_settings`, ключ `roadmap.integration.health`, значение `{ authFailedAt, authOkAt, httpStatus }`.
- **«PAT отклонён» — это только ответ 401 на любой запрос или ошибка расшифровки PAT.** Ответ 403 сюда не относится: он означает нехватку прав на конкретный проект или область, а не мёртвый PAT. Такой 403 проявится как `import_failing` или `sync_errors` по проекту.
- `authFailedAt` пишет `RoadmapIntegrationService.request` при ответе 401 и `getCredentials()` при ошибке расшифровки (она падает раньше, чем доходит до `request`). `authOkAt` пишет `request` при успешном ответе.
- Писать **только при смене состояния** относительно БД. Состояние из БД можно кэшировать в памяти не дольше 60 секунд: устаревший кэш на одном из инстансов даст лишнюю запись, но не неправильное состояние.
- Ответ на `testConnection` с ещё не сохранённым PAT (форма проверки) это состояние не меняет.

Миграция одна, аддитивная: `apps/api/prisma/migrations/<YYYYMMDDHHMMSS>_roadmap_notifications/`.

## 4. Виды проблем

| `kind` | Область | Условие «есть проблема» | Кому | Заголовок (пример) | Куда ведёт |
|---|---|---|---|---|---|
| `sync_errors` | проект | ≥ 1 назначение проекта в статусе `error` | админы + планировщики проекта | «Ошибки отправки в Azure: 5 назначений · Проект X» | план проекта с фильтром по статусу, если он есть; иначе «Интеграции → Проекты → Подробности» |
| `sync_conflicts` | проект | ≥ 1 назначение в статусе `conflict` | админы + планировщики проекта | «Конфликты с Azure: 2 назначения · Проект X» | то же |
| `import_failing` | проект | `importFailingSince` не пуст и `now − importFailingSince ≥ 15 мин` | админы + планировщики проекта | «Не удаётся обновить проект из Azure · Проект X» + текст ошибки | «Интеграции → Проекты» |
| `azure_auth` | глобально | интеграция подключена и `authFailedAt > authOkAt` (или `authOkAt` пуст) | только админы | «Azure DevOps отклоняет PAT (HTTP 401)» | «Интеграции → Подключение» |
| `webhook_silent` | проект | у проекта уже был webhook (`lastWebhookAt` не пуст), импорт по опросу нашёл изменения (`lastImportChangedAt`), а webhook не приходил дольше 30 минут после этого: `lastImportChangedAt − lastWebhookAt > 30 мин` | только админы | «Webhook из Azure не приходит · Проект X» | «Интеграции → Webhook» |

Пояснения:
- **`webhook_silent` не срабатывает на тихих проектах.** «Webhook молчит» само по себе нормально, если в Azure ничего не меняется. Проблема есть, только когда опрос видит изменения, а webhook о них не сообщил.
- **Проекты без записи в Azure.** Для `sync_errors` и `sync_conflicts` считаются только проекты, у которых запись в Azure включена (режим manual или auto, и проект входит в область записи). Остальные проекты не участвуют.
- **Одна причина — одно уведомление.** Если отклонён PAT, падают и импорт, и отправка назначений. Пока открыт `azure_auth`, новые `import_failing`, `sync_errors` и `webhook_silent` **не открываются**. Уже открытые эпизоды не трогаются.
  - После того как `azure_auth` закрылся, сторож работает как обычно. Импорт к этому времени снова проходит, и `import_failing` не откроется.
  - Назначения в `error` сами не исправляются: их нужно отправить снова. Поэтому `sync_errors` откроется уже после закрытия `azure_auth`. Это нужное уведомление: оно говорит, что осталось доделать после починки PAT.

## 5. Сторож

### 5.1. Запуск
`RoadmapAlertsService.evaluate()` — `@Interval(60_000)`, файл `apps/api/src/modules/roadmap/roadmap-alerts.service.ts`. Запускается на всех инстансах. Корректность обеспечивают условные `updateMany` и уникальные индексы, а не блокировка.

### 5.2. Шаг
1. Посчитать агрегаты по всем проектам одним-двумя запросами. Числа назначений `error` и `conflict` по проектам получить через join `allocation → work_item` (`$queryRaw` с `GROUP BY`). Состояния проектов прочитать из `RoadmapAzureProjectState`, глобальное состояние — из `system_settings`. Проходить по назначениям в цикле нельзя: проект может содержать до 3 000 назначений.
2. Для каждого ключа вычислить, выполнено ли условие, и сравнить с проблемой в БД:
   - **Условие выполнено, проблемы нет или она `resolved`** → открыть. Это условный `updateMany` с `where: { key, state: 'resolved' }` (или `create` для нового ключа, конфликт по unique ловим), он ставит `state: open, generation: +1, openedAt: now, clearSince: null, details`. Если строка обновлена, этот инстанс выиграл: он вычисляет получателей и делает `createMany({ skipDuplicates: true })` уведомлений. Если не обновлена, этим занимается другой инстанс.
   - **Условие выполнено, проблема `open`** → обновить `details` (счётчик) и сбросить `clearSince`. Новых уведомлений нет. Текст уже созданных уведомлений не меняется. В списке показывается актуальный счётчик из `details` проблемы (§6).
   - **Условие ложно, проблема `open`** → если `clearSince` пуст, поставить `now`. Если `now − clearSince ≥ 10 мин`, закрыть: условный `updateMany` с `where: { key, state: 'open' }` ставит `state: resolved, resolvedAt: now, resolution: 'fixed'`.
   - **Проблема потеряла смысл** → закрыть сразу, без задержки, с `resolution: 'obsolete'`. Случаи:
     - проект удалён или больше не импортирован;
     - для `sync_errors` и `sync_conflicts` — проект выведен из записи в Azure или запись выключена;
     - для `azure_auth` — интеграция отключена.

     Удалённый проект и так удаляет проблему каскадом, отдельно обрабатывать его не нужно.
   - Порядок внутри шага: сначала `azure_auth`, потом проектные виды. Так подавление из §4 видит актуальное состояние.
3. Раз в сутки (первый шаг после полуночи по серверу) удалить уведомления старше 90 дней и закрытые проблемы без уведомлений.

### 5.3. Защита от мигания
Проблема закрывается, только если условие было ложным **10 минут подряд**. Повторная отправка назначения с ошибкой (`error → pending → sending → error`) занимает секунды и не порождает «исправлено» и новую «проблему».

### 5.4. Получатели
Вычисляются в момент открытия эпизода (снимок):
- админы: активные пользователи с ролью `admin`;
- планировщики проекта: email из `RoadmapProjectAccess` с `role = 'planner'` → активные `User` с тем же email без учёта регистра;
- объединить и убрать дубли по `userId`.

Тот, кто получил доступ после открытия эпизода, уведомление по нему не получает, но получит при следующем. Это допустимо для v1.

### 5.5. Тексты
Готовые русские строки формирует API в одном месте — функция `formatAlert(kind, details, projectName)`. Текст ошибки из Azure (`lastImportError`, пример `azureSyncError`) обрезать до 300 символов и пропустить через ту же очистку, что и журнал синхронизации. PAT в тексте быть не может, так как он не попадает в тексты ошибок, но это проверяется тестом.

## 6. API

Модуль внутри `roadmap` (контроллер `roadmap-notifications.controller.ts`). Доступен любому авторизованному пользователю. Видны только **свои** уведомления, фильтр всегда по `request.user.id`.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/roadmap/notifications?cursor=&limit=30` | `{ items: NotificationDto[], nextCursor }`, новые сверху |
| GET | `/roadmap/notifications/summary` | `{ unread: number, activeUnread: number }` |
| POST | `/roadmap/notifications/:id/read` | `204` (чужой id → `404`) |
| POST | `/roadmap/notifications/read-all` | `204` |

`NotificationDto`: `{ id, kind, projectId, projectName, title, body, link, createdAt, readAt, active: boolean, current: { count?, httpStatus? } }`, где:
- `active` — проблема этого эпизода всё ещё открыта;
- `current` — актуальные данные проблемы (например, сейчас уже 2 ошибки, а не 5), если эпизод активен;
- `link` — относительный URL внутри веб-приложения. Его формирует API, чтобы маршруты жили в одном месте.

DTO и zod-схемы — в `packages/shared` рядом с прочими roadmap-типами.

## 7. Веб

### 7.1. Колокольчик
- **Где.** `RoadmapFrame.tsx`, правая группа кнопок, перед `TourLauncherIcon`. Стиль как у соседних кнопок (`size-9 rounded-lg border bg-card`), иконка `Bell` из `lucide-react`. В скелетоне шапки (`RoadmapFrameSkeleton.tsx`) — место под кнопку.
- **Счётчик.** Бейдж с `activeUnread` (непрочитанные и ещё актуальные). Если таких нет, но есть непрочитанные исправленные, показать точку без числа. Если нечего показывать, бейджа нет.
- **Опрос.** `summary` раз в 60 секунд и при фокусе окна. Список загружается при открытии поповера.

### 7.2. Список (поповер `shared/ui/popover`)
```
┌ Уведомления ─────────────── Прочитать все ┐
│ ● Ошибки отправки в Azure: 2 назначения   │
│   Проект Alpha · 12 мин назад      [акт.] │
│ ● Azure DevOps отклоняет PAT (HTTP 401)   │
│   3 ч назад                        [акт.] │
│   Не удаётся обновить проект из Azure     │
│   Проект Beta · вчера          ✓ исправлено│
│                     Показать ещё          │
└───────────────────────────────────────────┘
```
- Непрочитанные отмечены точкой. Клик по пункту отмечает его прочитанным и ведёт по `link`.
- У активных показывается актуальный счётчик (`current`). У закрытых — пометка «исправлено» (`fixed`) или «больше не актуально» (`obsolete`). Для этого в `NotificationDto` добавить поле `resolution`.
- Обязательны состояния загрузки, пустое («Всё спокойно — проблем с синхронизацией нет») и ошибки (через `ErrorNotice`).
- На ширине 375 px поповер занимает ширину экрана минус отступы, без горизонтального скролла.

### 7.3. Демо-режим
Добавить методы в `roadmapDemo.ts`/`roadmapDemoStore.ts`: чтение возвращает пустой список и нули, запись — no-op.

## 8. Сквозные требования
- Миграции только аддитивные, в новой папке. Применённые не трогать.
- Стиль кода как в соседних файлах, чужой код не переформатировать.
- Масштаб: до 20 000 work items и 3 000 назначений на проект. Сторож работает только через агрегаты, один шаг укладывается в < 1 с на таком объёме.
- Ошибка внутри сторожа логируется и не роняет остальные фоновые задачи. Следующий шаг повторяет попытку.
- Документация: раздел «Уведомления» в `docs/13-roadmap.md`. В нём описать, какие виды проблем бывают, кому приходят и когда закрываются.

## 9. Тесты (обязательно)

Сторож (unit, с моком Prisma или на тестовой БД, как в соседних `*.spec.ts`):
1. Ошибка появилась — открывается эпизод, получатели получают ровно одно уведомление.
2. Пять шагов подряд с растущим числом ошибок не создают ни одного нового уведомления, `details` обновляются.
3. Условие ложно 5 минут, потом снова истинно — эпизод не закрывался, новых уведомлений нет.
4. Условие ложно 10 минут — эпизод закрыт. Повторное появление открывает `generation + 1` и создаёт новые уведомления.
5. Два параллельных `evaluate()` (имитация двух инстансов) создают одно уведомление на пользователя.
6. Пока открыт `azure_auth`, не открываются `import_failing`, `sync_errors` и `webhook_silent`. После его закрытия оставшиеся назначения в `error` открывают `sync_errors`.
6а. Выключение записи в Azure для проекта сразу закрывает его `sync_errors` с `resolution: 'obsolete'`, без 10-минутной задержки.
7. `webhook_silent` не срабатывает на проекте без изменений и на проекте, где webhook ни разу не приходил.
8. Получатели: email планировщика в другом регистре находится, неактивные пользователи исключены, админ-планировщик получает одно уведомление.
9. В заголовке и теле нет PAT и секрета webhook, даже если текст ошибки Azure их содержит.

API (e2e, как `roadmap-access.e2e-spec.ts`):
10. Пользователь видит только свои уведомления. `read` чужого id даёт `404`.
11. `summary` считает `activeUnread` с учётом закрытых эпизодов.

Запись здоровья:
12. Неудачный импорт (в том числе через webhook) ставит `importFailingSince`, повторная неудача его не сдвигает, успешный импорт сбрасывает.
12а. 401 меняет `roadmap.integration.health` один раз, а не на каждый запрос. 403 его не меняет. Ошибка расшифровки PAT в `getCredentials()` ставит `authFailedAt`.
12б. `lastImportChangedAt` обновляет импорт по cron, а импорт по webhook — нет.

## 11. Развитие после v1 (не делать сейчас)
- **Внешние каналы.** Отдельный отправитель читает новые `RoadmapNotification` и шлёт письмо или сообщение в Telegram. Модель данных менять не нужно.
- **Точечные события** (гибрид). Например, «вам выдали доступ к проекту» или дайджест «перегрузка людей по кварталу». Это `RoadmapNotification` без `alertId`. Если пойдём этим путём, `alertId` станет nullable.
- **Личные настройки:** отписаться от вида или проекта.

## 12. Допущения и решения, принятые без заказчика
Проверить при чтении, любое можно поменять:
1. **Только канал внутри приложения.** Предполагается, что планировщики и администраторы заходят в Roadmap регулярно. Если нет, в первую очередь нужны внешние каналы (§11).
2. **Получатели.** Об ошибках, конфликтах и импорте узнают админы и планировщики проекта. О PAT и webhook — только админы. Наблюдатели (`viewer`) не получают ничего.
3. **Пороги.** Импорт считается сломанным через 15 минут неудач. «Исправлено» ставится только после 10 минут без проблемы. Webhook считается «молчит», если отстаёт от найденных опросом изменений на 30 минут. Уведомления хранятся 90 дней.
4. **«PAT отклонён» — только 401 и ошибка расшифровки.** Ответ 403 считается проблемой проекта, а не PAT.
5. **Пока PAT отклонён, проектные проблемы не открываются.** Ошибки отправки, оставшиеся после починки PAT, приходят отдельным уведомлением.
6. **Две пометки при закрытии.** «Исправлено» и «больше не актуально» различаются, чтобы не говорить «исправлено», когда никто ничего не чинил.
7. **Текст уведомления — снимок, счётчик — живой.** Текст фиксируется в момент открытия, а актуальное число берётся из проблемы.

## 13. Как проверять
1. `npm run build -w @tracker/shared`, `npm run test -w @tracker/api`, `npm run lint`.
2. Локально:
   - испортить PAT в `.env` → в течение ~1 мин у админа появляется «Azure DevOps отклоняет PAT»;
   - вернуть PAT → через ~10 мин уведомление помечено «исправлено».
3. Вручную перевести назначение в `error` (SQL) → одно уведомление у админа и планировщика проекта. Через 10 минут после возврата статуса — «исправлено».
4. Запустить два инстанса API → дублей нет.
5. Шапка на 375 px: колокольчик помещается, поповер без горизонтального скролла.
